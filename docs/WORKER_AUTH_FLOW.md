# Worker Auth Flow

## 1. 문서 목적

이 문서는 BuildOn Work의 근로자 회원가입, 로그인, 프로필 저장, 소개자 정보 저장, 로그인 후 이동 흐름을 실제 구현하기 전에 데이터 흐름과 보안 기준을 정리하기 위한 설계 문서입니다.

현재 단계에서는 화면, API, DB 구조, migration, mock 데이터를 수정하지 않습니다. 이 문서는 다음 구현 단계에서 무엇을 만들고 무엇을 제외할지 결정하는 기준으로 사용합니다.

## 2. 현재 상태

- Supabase 프로젝트 생성 완료
- migration SQL 실행 완료
- `users`, `workers`, `referrals` 테이블 생성 완료
- 주요 서비스 테이블 생성 완료: `companies`, `sites`, `jobs`, `applications`, `attendance`, `inquiries`, `notifications`
- Supabase browser/server client 설정 완료
- Vercel 환경변수 등록 완료
- Production 배포 READY 확인 완료
- 아직 실제 회원가입/로그인 기능은 없음
- 아직 실제 데이터 저장 기능은 없음
- 현재 근로자, 관리자 화면은 mock 데이터 기반

## 3. 1차 근로자 회원가입 목표

1차 구현 목표는 근로자가 계정을 만들고, 기본 프로필과 선택 입력인 소개자 정보를 저장할 수 있는 최소 흐름입니다.

- 근로자가 이메일과 비밀번호 기반으로 가입한다.
- 근로자 기본 정보로 이름, 전화번호, 선호 지역, 선호 직종, 선호 지급 조건을 입력한다.
- 소개자가 있을 경우 소개자 이름과 전화번호를 선택 입력으로 받는다.
- 가입 완료 후 근로자를 `/worker/jobs`로 이동시킨다.
- 관리자 화면에서 가입자별 소개자 정보를 확인할 수 있는 구조를 준비한다.

1차 구현에서 소개 수당 자동 계산, 자동 지급, 계좌번호 입력, 관리자 지급 처리 기능은 만들지 않습니다.

## 4. 회원가입/로그인 화면 경로 제안

- 근로자 회원가입: `/worker/signup`
- 근로자 로그인: `/worker/login`
- 가입 완료 후 이동: `/worker/jobs`
- 로그인 완료 후 이동: `/worker/jobs`
- 내 정보 확인 유도 경로: `/worker/my`

초기에는 가입과 로그인 성공 후 모두 `/worker/jobs`로 이동하는 것을 권장합니다. 근로자에게 가장 중요한 첫 행동이 일자리 확인이기 때문입니다. 단, 가입 직후 프로필 보완을 더 중요하게 판단한다면 `/worker/my`로 바꿀 수 있습니다.

## 5. 회원가입 입력 항목

필수 항목:

- 이름
- 전화번호
- 이메일
- 비밀번호
- 선호 지역
- 선호 직종
- 선호 지급 조건

선택 항목:

- 소개자 이름
- 소개자 전화번호

1차 구현 제외 항목:

- 주민등록번호
- 계좌번호
- 신분증
- 사업자등록증
- 자격증 파일
- 안전교육 이수증
- 자동 정산 정보

소개자 입력 안내 문구 예시:

> 소개자가 있다면 이름과 전화번호를 입력해 주세요. 입력된 소개자 정보는 가입 경로 확인과 소개 수당 검토 목적으로만 사용됩니다.

## 6. 데이터 저장 흐름

권장 저장 순서:

1. Supabase Auth에 인증 사용자를 생성한다.
2. 생성된 `auth.users.id`와 같은 id로 `public.users`에 기본 사용자 정보를 저장한다.
3. `public.workers`에 근로자 프로필을 저장한다.
4. 소개자 이름 또는 전화번호가 입력된 경우 `public.referrals`에 소개자 정보를 저장한다.
5. 가입 완료 후 `/worker/jobs`로 이동한다.

현재 migration 기준 실제 관계:

- `public.users.id`는 `auth.users(id)`를 참조한다.
- `public.workers.user_id`는 `public.users(id)`를 참조한다.
- `public.referrals.worker_id`는 `public.workers(id)`를 참조한다.

따라서 구현 시에는 Auth 사용자 생성 후 `users`, `workers`, `referrals` 순서로 저장하는 흐름이 가장 자연스럽습니다.

## 7. users / workers / referrals 관계

`users` 테이블:

- `id`가 primary key입니다.
- `auth.users(id)`를 참조합니다.
- 역할, 이름, 전화번호, 이메일, 상태, 마지막 로그인 시각을 저장합니다.

`workers` 테이블:

- `user_id`가 `public.users(id)`를 참조합니다.
- 근로자의 선호 지역, 선호 직종, 선호 지급 조건, 경력 요약, 프로필 상태를 저장합니다.
- 한 사용자당 하나의 근로자 프로필을 갖도록 `user_id`가 unique입니다.

`referrals` 테이블:

- `worker_id`가 `public.workers(id)`를 참조합니다.
- 소개자 이름, 소개자 전화번호, 검토 상태를 저장합니다.
- 한 근로자당 하나의 소개자 기록을 갖도록 `worker_id`가 unique입니다.
- `review_status` 기본값은 `pending_review`입니다.

## 8. 소개자 정보 저장 정책

- 근로자 회원가입 중 소개자 이름과 전화번호를 선택 입력으로 받습니다.
- 소개자 정보가 입력된 경우에만 `referrals` 테이블에 저장합니다.
- `review_status`는 기본적으로 검토 대기 상태로 둡니다.
- 관리자는 가입자별 소개자 정보를 확인할 수 있습니다.
- 소개 수당은 시스템 자동 지급이 아니라 운영자가 별도 기준에 따라 수동 검토합니다.
- 자동 정산, 자동 송금, 계좌 등록은 1차 구현 범위에서 제외합니다.

## 9. 로그인 흐름

권장 로그인 흐름:

1. 근로자가 `/worker/login`에 접속한다.
2. 이메일과 비밀번호를 입력한다.
3. Supabase Auth로 로그인한다.
4. 로그인 성공 시 `/worker/jobs`로 이동한다.
5. 로그인 실패 시 기본 오류 안내를 표시한다.

초기 구현에서는 카카오 로그인, 네이버 로그인, 문자 인증, 휴대폰 본인인증을 제외합니다.

전화번호 로그인은 초기부터 도입하지 않는 것을 권장합니다. 1차 구현에서는 전화번호를 프로필 정보로만 저장하고, 로그인 ID는 이메일로 시작하는 편이 Supabase Auth 기본 흐름과 구현 안정성 측면에서 단순합니다.

## 10. RLS 및 보안 기준

현재 migration 기준 확인 내용:

- `users`는 인증 사용자가 자기 정보 또는 관리자가 조회할 수 있습니다.
- `users`는 인증 사용자가 자기 정보 또는 관리자가 수정할 수 있습니다.
- `workers`는 해당 근로자 본인 또는 관리자가 조회/수정할 수 있습니다.
- `referrals`는 해당 근로자 본인 또는 관리자가 조회할 수 있습니다.
- `referrals` 생성은 해당 근로자 본인의 기록에 한정됩니다.
- `referrals` 수정은 관리자만 가능합니다.
- `sites`와 `jobs` 조회는 authenticated 사용자 기준으로 열려 있습니다.
- `sites`와 `jobs` 생성/수정은 회사 owner 또는 admin으로 제한됩니다.
- anon 전체 공개 정책은 확인되지 않았습니다.

보안 기준:

- client에서는 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`만 사용합니다.
- service_role key를 client에서 사용하지 않습니다.
- secret key를 사용하지 않습니다.
- DB password와 connection string을 사용하지 않습니다.
- `.env.local`은 Git에 커밋하지 않습니다.
- 근로자 전화번호와 소개자 전화번호는 관리자 운영 목적 외부로 노출하지 않습니다.

## 11. 관리자 화면의 소개자 확인 방향

1차 구현에서는 별도 `/admin/referrals` 화면을 만들지 않고, `/admin/workers` 안에서 근로자별 소개자 정보를 함께 확인하는 방향을 권장합니다.

표시 후보:

- 가입자 이름
- 가입자 연락처 일부
- 가입일
- 소개자 이름
- 소개자 전화번호 일부
- `review_status`
- 지급 여부가 아니라 검토 상태

1차 제외:

- 지급하기 버튼
- 자동 수당 계산
- 계좌 이체
- 정산 이력
- 엑셀 다운로드

## 14. 구현 전 확인 질문

- 가입 방식은 이메일/비밀번호로 시작할 것인가?
- 전화번호는 로그인 ID가 아니라 프로필 정보로만 둘 것인가?
- 소개자 전화번호는 선택 입력으로 둘 것인가?
- 가입 완료 후 `/worker/jobs`로 보낼 것인가, `/worker/my`로 보낼 것인가?
- 관리자 소개자 확인은 `/admin/workers` 안에서 먼저 처리할 것인가?
- 로그인하지 않은 사용자가 `/worker/jobs`를 볼 수 있게 둘 것인가?
- 일자리 목록은 가입 전에도 볼 수 있게 할 것인가?
- 지원하기는 로그인 후에만 가능하게 할 것인가?
